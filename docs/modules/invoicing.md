# Invoicing / Billing Module

## Overview

The Billing module generates invoices and delivery challans with GST breakup. It supports three billing modes (dispatch-based, FG-based, and direct), multiple document types (Invoice and Challan), and enforces billing constraints at the database level. Posted invoices are locked and cannot be modified.

> The Billing / Invoicing section starts at roughly line 24528 in `Code.gs` (`createInvoice`).

## Tables

| Table | Purpose |
|-------|---------|
| `invoices` | Invoice/challan header (bill-to/ship-to, transport, GST, status) |
| `invoice_lines` | Line items linked to SO lines with billing snapshots |
| `invoice_sequences` | Invoice number sequences by financial year and prefix |
| `billing_division_bulk_fix` | Staging table for the bulk billing-division correction routine |

## Document Types

| Type | Description |
|------|-------------|
| `INVOICE` | Standard tax invoice with GST |
| `CHALLAN` | Delivery challan (no tax) |

Document type is stored in `invoices.document_type` and determines number prefix and tax treatment.

## Invoice Number Format

Generated by `_billingGenerateDocumentNo_(documentType, invoiceDate)`:
- Invoice: `PSE-H/{FY}/{SEQ}` (e.g., `PSE-H/2526/0001`)
- Challan: `DC-H/{FY}/{SEQ}` (e.g., `DC-H/2526/0001`)
- Sequences tracked per FY in `invoice_sequences`

## Invoice Status Lifecycle

```
DRAFT ──> POSTED (locked, invoice lines cannot be edited/deleted)
  |
  └──> CANCELLED (soft cancel)
```

Constraint: `invoice_status_chk` restricts status to DRAFT/POSTED/CANCELLED.

When an invoice is POSTED:
- `posted_at` timestamp is set
- Trigger `trg_lock_invoice_lines` prevents any UPDATE or DELETE on its `invoice_lines`

## Billing Modes

### 1. Dispatch-Based Billing

Bills based on dispatched quantity:
- `dispatch_billable_qty` = dispatched_qty - billed_qty
- Uses data from `v_billing_dispatch_summary`

### 2. FG-Based Billing

Bills based on packed quantity minus FG adjustments:
- `fg_billable_qty` = packed_qty - billed_qty - fg_adjusted_qty
- Uses data from `v_billing_packing_summary` and `fg_stock_adjustments`

### 3. Direct Billing

Bills against order quantity directly:
- `direct_billable_qty` = order_qty - billed_qty
- Used for service items and manual billing

## GST Calculation

GST split is determined by comparing company state (Haryana) with client state:

- **Intra-state** (same state): CGST + SGST (each = GST% / 2)
- **Inter-state** (different state): IGST (= GST%)

The `_billingCalcTaxSplit_(clientState, gstPct, taxableAmount)` function handles this logic. Freight GST is calculated separately via `_billingCalcFreightTax_()`.

## Bill-to / Ship-to Address Resolution

The billing system resolves addresses from multiple sources:

1. **Client parties** (`client_parties` table) - Multiple bill-to/ship-to per client
2. **Client master** (legacy `clients` table fields) - Fallback addresses
3. **Manual entry** - User can enter custom addresses

`_billingBuildAddressChoices_()` builds a list of address options for the UI.

## Manual Invoices

The system supports creating invoices without existing SOs. `_billingCreateManualInvoice_()`:
1. Creates a temporary `sales_order` and `sales_order_lines` for the manual items
2. Creates the invoice and invoice_lines linking to these records
3. The manual SO number is auto-generated (e.g., `MNL-H/{FY}/{SEQ}`)

## Constraints / Triggers

| Mechanism | Purpose |
|-----------|---------|
| `ux_invoice_so_line` | One invoice line per SO line per invoice |
| `invoice_status_chk` | Status must be DRAFT, POSTED, or CANCELLED |
| `trg_lock_invoice_lines` | Prevents edit/delete of lines on posted invoices |
| `trg_sales_order_line_status_from_invoice` | Recomputes the parent SO line `status` whenever an invoice's status / posted_at / document_type / invoice_no changes |
| `trg_sales_order_line_status_from_invoice_line` | Recomputes the parent SO line `status` whenever an `invoice_lines` row is inserted / updated / deleted |

## Bulk Billing-Division Correction

When historical invoice lines were posted with the wrong `division` (a one-off data hygiene issue), the workflow is:

1. Identify offending rows via `v_billing_division_needs_fix`.
2. Load the correct (invoice_no, line_no, division) tuples into `billing_division_bulk_fix`.
3. Run the correction routine — it rewrites the division on the SO line and the matching invoice line and stamps `applied_at`. The trigger `trg_lock_invoice_lines` does not block this update because the column is whitelisted by the fix routine; in practice it runs against fields that aren't financial.

## Integration

- **Sales Orders**: Invoice lines reference SO lines; billing remarks flow from SO header; SO line status is auto-recomputed on every invoice change.
- **Dispatch**: Dispatch qty determines billable amount in dispatch mode.
- **FG Stock**: FG adjustments affect billable amount in FG mode.
- **Client Parties**: Bill-to / ship-to addresses resolved from `client_parties`.
- **Reports**: Invoice data feeds the billing register, unbilled dispatch, job profitability, and dispatch discrepancy reports.
