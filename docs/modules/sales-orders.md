# Sales Orders Module

## Overview

The Sales Orders module handles customer order entry, editing, approval workflows, and lifecycle management. It is the starting point of the entire ERP flow.

## Tables

| Table | Purpose |
|-------|---------|
| `sales_orders` | Order header (SO number, client, dates, transport, billing) |
| `sales_order_lines` | Line items (product, qty, rate, GST, approvals, **line-level status**) |
| `sales_order_rollup_cache` | Cached rollup of approval / WO statuses (parent-level) |

> The Sales Orders section starts at roughly line 10783 in `Code.gs` (`saveOrderWithKey`).

> The legacy `so_counters` table has been removed. SO numbers are now generated in Apps Script using the generic counter mechanism.

## SO Number Format

SO numbers are generated by `generateSalesOrderNumber(prefix, orderDate)`:

- Format: `{PREFIX}-{FY}/{SEQ}` (e.g., `SL-2526/0001`, `M-2526/0042`)
- `PREFIX`: `SL` for label/sticker orders, `M` for trading items
- `FY`: Financial year string (e.g., `2526` for April 2025 - March 2026)
- `SEQ`: Zero-padded to 4 digits

The `getFinancialYear(dt)` function returns the FY string. April is the start of the Indian financial year.

## Order Creation Flow

1. User fills order form in the web app (page: `order`).
2. `saveOrderWithKey()` is called with an idempotency key to prevent duplicates.
3. System generates SO number via `generateSalesOrderNumber()`.
4. Header inserted into `sales_orders`.
5. Lines inserted into `sales_order_lines`.
6. **The `trg_sales_order_lines_ensure_artwork` database trigger auto-creates the matching `artworks` row for each line** — no longer done by Apps Script.
7. Rollup cache updated by trigger `trg_sales_order_rollup_from_sales_orders`.
8. The per-line `status` column is seeded to `OPEN` and will then be auto-cascaded by the SO-line-status trigger family on any dispatch / invoice / parent-status change.

### Auto-Maintained Line Status

The `sales_order_lines.status` column is recomputed by a five-trigger cascade — see [business-rules.md](../database/business-rules.md#sales-order-line-status-cascade-triggers). The application layer never writes this column directly. The status reflects, in this order:

- Parent SO status (HOLD / CANCELLED bubble down).
- Dispatch totals (PARTIAL_DISPATCHED once any dispatch row exists; CLOSED when ordered qty is fully dispatched).
- Invoice totals (CLOSED only when the dispatched qty is also fully invoiced).

## Approval Workflow

Sales order lines require two independent approvals before they can proceed to work order creation:

1. **Accounts Approval** (`accounts_status`) - Finance team verifies pricing, credit terms
2. **Business Approval** (`business_status`) - Management approves the order

Functions:
- `updateSalesOrderLineApproval(payload)` - Update single line approval
- `bulkUpdateSalesOrderApproval(payload)` - Bulk approve/reject multiple lines

RBAC permissions control who can approve:
- `can_approve_accounts` on `SALES_ORDER_APPROVAL` module
- `can_approve_business` on `SALES_ORDER_APPROVAL` module

## SO Listing and Rollup Cache

The `sales_order_rollup_cache` table is maintained by three triggers:
- `trg_sales_order_rollup_from_lines` - When SO lines change
- `trg_sales_order_rollup_from_sales_orders` - When SO header changes
- `trg_sales_order_rollup_from_work_order_jobs` - When WO jobs change

This cache provides:
- `accounts_status` / `business_status` - Rolled up from all lines (PENDING if any pending, APPROVED if all approved)
- `wo_status` - PENDING or CREATED based on work_order_jobs existence
- `line_count` / `total_qty` - Summary counts
- `can_edit` / `can_hold` / `can_cancel` - UI state flags

The `v_sales_orders_list_fast` view joins `sales_orders` with `clients` and `sales_order_rollup_cache` for the listing page.

## SO Lifecycle

```
OPEN ──> HOLD ──> OPEN (reopen)
  |
  └──> CANCELLED (terminal, blocks all downstream)
```

Cancelled SOs are excluded from WO candidate views and billing.

## Integration with Other Modules

- **Artwork**: Auto-created by the `trg_sales_order_lines_ensure_artwork` DB trigger on every SO line insert / identifying-field update.
- **Work Orders**: SO lines become WO candidates after approval (`v_workorder_candidates`).
- **Billing**: SO lines are referenced by `invoice_lines` for billing.
- **Reports**: `v_report_planning_lines` / `_enriched` track SO lines through the full lifecycle; pre-WIP / WIP / billing register views all join back here.
